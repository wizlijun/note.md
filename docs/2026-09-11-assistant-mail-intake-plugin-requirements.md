# 助理邮箱接管插件需求规格

日期：2026-09-11

状态：需求基线，待技术设计

适用范围：单一用户、一个专用助理邮箱、Agent 默认只读并可在显式授权后执行受控清理

## 0. 文档权威性与规范语言

本文定义“助理邮箱接管插件”要解决的问题、必须具备的业务能力、数据边界和验收标准。后续产品设计、技术设计、实现与测试均应以本文为需求基线；若产生冲突，必须显式修订本文，不能在实现中静默改变需求。

本文不决定部署方式、云服务、存储产品、数据库、接口协议、编程语言或模型供应商。

- **必须／不得**：强制要求，不满足即不能验收。
- **应该／不应该**：默认要求；偏离时必须说明理由及风险。
- **可以**：可选能力，不构成首版验收门槛。

本文用以下术语区分邮件处理边界：

- **投递**：邮件已经到达专用邮箱，尚未判断是否适合处理。
- **准入**：邮件通过范围与安全检查，可以作为助理事件的来源。
- **隔离**：邮件因敏感、可疑或不确定而不进入正常处理，等待人工处置。
- **拒绝**：邮件不被保存为可检索内容，也不生成事件；只保留不含秘密的必要审计结果。
- **披露**：某项邮件信息经过授权和脱敏后可以被 Agent 读取。

## 1. 产品目标

插件为用户提供一个独立于私人主邮箱和工作主邮箱的专用信息入口，持续接收会形成以下任一结果的通知型邮件：

1. 明确日程或行程；
2. 必须在某个时间前完成的动作；
3. 已有安排的关键变化；
4. 付款、退款、出票、预约等事项的闭环证据；
5. 足以影响用户当天决策、承诺、关系、精力、家庭生活或安全的异常。

插件应把邮件转换为可回源、可去重、可更新状态的结构化事件，使获授权 Agent 能回答：

- 今天有什么必须由用户本人决定或确认？
- 哪项承诺、付款、行程或预约即将失信或失效？
- 最近发生了什么关键变化？
- 哪些事项只是已安排，尚未真正完成？
- 哪些内容只需保留，不值得占用用户注意力？

插件的价值不在于复制一个普通收件箱，而在于把外部通知变成可靠的“时间、变化、责任和闭环”信号。

## 2. 非目标

首版明确不做：

- 不成为私人主邮箱或工作主邮箱的替代品；
- 不收集所有邮件，不追求通信完整归档；
- 不代用户发信、回复、承诺、致歉、确认或拒绝；
- 不支付账单，不输入验证码，不修改自动扣款；
- 不订票、退票、改签、取消酒店或修改预约；
- 不点击邮件中的登录、付款、改签或身份验证链接；
- 不把邮件正文中的指令当作 Agent 指令；
- 不依据邮件作医疗、法律、投资或信用判断；
- 不替代 Timeline、日历、聊天、任务、联系人和长期记忆；
- 不自动向 Timeline、日历、任务系统或长期记忆写入内容；
- 不把他人的责任自动转换为用户的责任；
- 不因“未发现完成邮件”就断言事项没有完成。

## 3. 使用者与信任边界

### 3.1 角色

- **用户本人**：邮箱及其中个人信息的授权主体和最终决策者。
- **邮箱管理员**：配置来源、转发、保留、删除和访问权限；可以与用户为同一人。
- **获授权 Agent**：默认只读取必要信息，生成提醒、风险提示和决策建议；只有在用户对精确删除计划显式授权后，才可通过受控服务执行该计划。
- **邮件发送方**：航空公司、银行、酒店、医院、学校、服务商、合作方等外部主体；始终视为外部输入。

### 3.2 基本信任规则

- 邮件正文、HTML、附件、二维码、链接和转发链全部是不可信输入。
- 发件人名称不是身份凭据；插件必须保留足够的原始来源信息，供后续判断来源可信度。
- 用户手动转发表示“这封邮件值得助理关注”，不等于用户确认其内容真实、责任成立或授权执行动作。
- Agent 对邮箱的默认权限必须是只读；“用户授予较多个人上下文”不等于授权外部行动。清理或删除必须由 Agent 先生成包含精确对象和影响范围的计划，再由用户通过可信界面对该计划显式授权；授权不得扩展到发信、付款或其他外部行动。
- 邮件只能提供线索和证据，不能自行扩大 Agent 的权限。

### 3.3 来源可信层级

插件必须保留邮件的投递方式，并区分：

- **直接认证来源**：邮件由声称的业务发送方直接投递，且来源认证信息足以支持该判断；
- **可信转发来源**：邮件由用户认可的邮箱或规则转发，但只能证明转发渠道可信；
- **内层声称来源**：原始发送方只出现在转发正文、附件或引用内容中；
- **不可核验来源**：无法可靠判断直接发送方或原始发送方。

转发包装层的认证结果不得继承给内层声称的原始发送方。来源可信度只影响证据判断，不能绕过敏感信息、提示词注入或外部行动限制。

## 4. 单邮箱接管范围

### R1 一个专用邮箱

系统只管理一个专用邮箱地址，例如 `assistant@用户域名`。地址名称必须可配置，本文示例不构成命名要求。

首版只管理一个固定专用收件地址；Worker 必须始终按外层 SMTP envelope recipient 精确校验该地址，该门禁不能关闭。发件人门禁由用户在可信插件窗口控制：首次配置 Gmail 等供应商的转发时可以进入最长一小时的“验证期开放”模式，以接收供应商系统发送的转发确认邮件；界面必须显著提示此时任何 envelope sender 都可向专用地址投递，到期必须自动恢复严格过滤。转发验证完成后，用户保存自己的唯一转发邮箱并主动开启严格过滤；此后其他 envelope sender 必须在任何正文或附件持久化之前拒绝，只可留下不含邮件内容的拒绝计数或必要审计。

转发邮件中的内层原始发送方仍必须按来源可信层级记录；通过指定 Gmail 转发只能证明转发渠道可信，不能证明内层内容真实。

### R2 通知型入口

被主动发送或转发到该邮箱的邮件必须以“形成事件、期限、变化、异常或闭环证据”为目的。普通讨论、长邮件往来和仅供阅读的内容不应投递。

### R3 邮件不是完整上下文

插件必须能明确表示自己的覆盖范围和最新处理时间。Agent 不得因为邮箱中没有记录，就声称用户没有其他承诺、关系事项、健康风险或家庭安排。

## 5. 应接收的邮件

### 5.1 准入原则

满足以下至少一项的邮件才应通过准入：

- 包含明确日期、时间、时区或时间窗口；
- 包含必须回复、支付、准备、到场、签署、续费、取消或核对的动作；
- 改变已经确认的时间、地点、金额、状态或参与安排；
- 证明一项动作已完成、失败、取消、退款或入账；
- 包含可能造成失信、罚息、信用影响、错过交通、错过家庭事项或服务中断的异常。

### 5.2 业务分类

业务分类最终作用于事件，而不是强迫整封邮件只能属于一类。一封邮件可以产生多个不同分类的事件；每个事件必须有且只有一个主要业务分类，并可以带次要语境标签。

| 分类标识 | 业务范围 | 应进入的典型邮件 | 必须识别的核心信息 |
| --- | --- | --- | --- |
| `travel.transport` | 航班、高铁、铁路、轮渡、租车、接送 | 预订、出票、值机、变更、延误、取消、退改、退款 | 出发与到达时间、时区、站点、航站楼、班次、状态、退改窗口 |
| `travel.lodging` | 酒店、民宿及其他住宿 | 预订确认、入住提醒、变更、取消、预授权或扣款失败 | 城市、入住退房、房晚覆盖、取消期限、付款状态 |
| `calendar.commitment` | 会议、活动、宴请、课程、公开活动 | 邀请、报名、确认、改期、取消、入场提醒 | 开始结束时间、地点、参与方、回复期限、准备要求 |
| `response.commitment` | 需要回复或维护关系的重要来信 | 用户选定的客户、员工、家人或朋友来信，以及感谢、祝贺、安慰、修复关系或确认预期的提醒 | 对象、关系、期望动作、明确期限、是否必须本人联系 |
| `work.commitment` | 必须由用户本人处理的工作义务 | 电子签署、董事会期限、客户答复、投标、合同续签通知 | 决定或交付内容、明确责任人、期限、是否必须本人 |
| `finance.bill` | 有明确付款义务的账单 | 信用卡出账、还款到期、保险、物业、水电、税费提醒 | 机构、卡号或账户末四位、金额、币种、最低还款额、到期日 |
| `finance.payment` | 付款及退款的状态变化 | 自动扣款安排、扣款失败、支付成功、到账、退款 | 付款对象、金额、状态、发生时间、是否真正入账 |
| `subscription.renewal` | 周期性服务与合约 | 软件、会员、域名、云服务、通信套餐续费或涨价 | 续费日、金额变化、取消期限、服务中断后果 |
| `identity.admin` | 身份、政府与行政手续 | 签证、护照预约、驾照、保险、税务、申请补件、证件到期 | 申请状态、预约时间、补件内容、明确期限 |
| `health.appointment` | 健康相关安排 | 医院、牙医、体检、疫苗、康复、续方预约及变更 | 时间、地点、准备要求、取消期限；不提取诊断结论 |
| `family.life` | 家庭与日常生活 | 学校活动、家人预约、维修、保洁、搬家、重要配送 | 时间窗口、地点、联系人、需要谁到场或准备什么 |
| `relationship.occasion` | 关键关系中的正式节点 | 婚礼、生日活动、葬礼、正式邀请、礼物送达、需要回复的私人活动 | 对象、关系动作、活动时间、回复或致谢期限 |
| `device.service` | 关键设备与基础服务 | 手机电脑维修、保修、网络停机、关键设备交付 | 服务窗口、中断风险、取件时间、备份或准备要求 |
| `reservation.ticket` | 非交通类预订与票务 | 餐厅、演出、赛事、展会及门票 | 时间、地点、人数、入场要求、取消期限 |

### 5.3 条件性接收

以下邮件默认不进入，只有满足额外条件时才可进入：

- 普通购物和物流：仅限重要物品、高价值物品或必须本人签收的明确时间窗口；
- 出租车、餐饮和日常消费小票：仅限报销期限、金额异常或行程核对确有需要；
- 普通交易提醒：仅限疑似重复扣款、异常金额、支付失败或影响后续服务；
- 工作通知：仅限来源明确表明用户本人负责、需要本人决定或需要本人亲自维护关系；
- 医疗通知：仅限预约、准备、取消和续方等行动信息，不接收完整病历或诊断材料。

无法可靠归入上述 14 类、但可能包含有效动作或期限的邮件，必须进入“待人工复核”，不能误判为无事项或静默丢弃。

## 6. 禁止进入的内容

以下内容不得主动发送或转发到该邮箱。供应商为建立转发关系而自动发送到专用地址的确认邮件是唯一的接入期例外：可信插件窗口可以让用户以纯文本查看并自行确认，但不得生成正常事件、进入 Agent 可搜索正文或被 Agent 代为点击：

- 一次性验证码、登录确认、Magic Link、密码重置、安全问题和恢复码；
- 账户登录异常、身份恢复和其他应由本人安全渠道处理的账户安全邮件；
- 银行、支付、证券或数字资产账户的密码、PIN、CVV、私钥和助记词；
- 身份证、护照、驾照或银行卡的完整扫描件；
- 完整信用卡号、完整银行账号和大量逐笔交易明细；
- 工资单、员工绩效、举报、申诉和其他高敏人事材料；
- 完整病历、诊断报告、影像资料、基因信息和高度敏感健康材料；
- 律师保密通信、未公开并购、商业秘密和受监管的机密材料；
- 与助理决策无关的私人通信、聊天转录和邮件讨论串；
- 广告、优惠券、积分推广、贷款推销、旅行推荐和普通营销邮件。

禁止内容仍可能被误投到专用邮箱。插件必须在“物理收到”之后区分以下处置：

- 以验证码、凭证、身份恢复、完整身份材料、高敏人事、完整病历或机密通信为主体的邮件必须隔离或拒绝，不得生成正常事件，也不得进入 Agent 可搜索的正文或片段；
- 合法账单、行程或预约通知中夹带逐笔明细、完整编号或其他非必要敏感字段时，可以只提取准入范围内的安全字段；原始敏感部分必须与 Agent 隔离；
- 凭证、验证码、私钥、助记词和恢复材料不得出现在事件、搜索结果、摘要、日志或审计详情中；
- 邮件远程图片和其他外部资源不得因收件、预览、解析或 Agent 查询而自动加载；
- 附件中的宏、脚本和其他主动内容不得执行。

## 7. 邮件记录要求

每封通过准入的邮件必须形成一个稳定的来源记录，至少保留以下业务信息：

- 稳定的内部标识；
- 原始邮件标识及足以可靠识别重复投递的证据；
- 原始发件地址、显示名称、收件地址和回复地址；
- 原始发送时间、系统接收时间及其时区；
- 主题、正文类型、附件清单和转发链存在性；
- 可用于判断来源可信度的邮件认证和转发信息；
- 当前处理状态、失败原因和最后处理时间；
- 由该邮件产生或更新的事件；
- Agent 可引用但不会暴露秘密的来源定位。

插件不得把“转发到助理邮箱的时间”误当成订单、会议、账单或行程发生时间。

### 7.1 邮件处理结果

每次投递必须得到且只能得到一个当前处理结果：

| 处理结果 | 含义 |
| --- | --- |
| `received_pending` | 已投递，尚未完成准入与解析 |
| `parsed_with_events` | 已完成解析，并生成或更新了至少一个事件 |
| `parsed_no_event` | 已成功理解，但不构成事件 |
| `partially_parsed` | 仅部分内容可处理，已明确未覆盖范围 |
| `needs_review` | 可能有行动价值，但分类、来源或关键字段不足以确定 |
| `quarantined` | 因敏感、可疑或安全原因被隔离，不向 Agent 披露正文 |
| `rejected` | 不在范围内或禁止处理，不保存为可检索内容 |
| `processing_failed` | 本应处理但发生失败，原因可见并允许受控重试 |

`parsed_no_event`、`rejected` 和 `processing_failed` 的含义不得混淆。重复投递可以共享同一个用户可见来源与事件，但每次投递和处理尝试仍须可审计。

## 8. 事件模型

### 8.1 邮件与事件的关系

- 一封邮件可以不产生事件，例如已成功识别为无行动价值的通知；无法确认含义的邮件必须进入待人工复核或处理失败，而不能算作“无事件”。
- 一封邮件可以产生多个事件，例如酒店确认同时包含入住、退房和免费取消期限。
- 多封邮件可以共同描述一个事件，例如预订确认、时间变更、取消和退款邮件。
- 事件必须能够回到一封或多封来源邮件；不能生成不可追溯的确定性事实。
- 邮件可以有初步路由标签，但业务分类以事件为准。每个事件必须有且只有一个主要业务分类，并可以带次要语境标签；紧急程度、敏感程度和是否需要本人处理必须作为独立属性，不能混入分类含义。

### 8.2 事件必备信息

每个事件至少必须表达：

- 稳定事件标识；
- 业务分类与事件类型；
- 一句话可读标题；
- 当前生命周期状态、变化标记、证据状态、期限状态及各自更新时间；
- 发生时间、开始时间、结束时间和决定期限中适用的字段；
- 时间的精度类型，以及每个精确时刻的明确时区或“时区待核对”；
- 相关对象、服务商、地点和责任人；
- 是否明确需要用户本人行动；
- 来源明确要求的动作及其原始期限；
- 来源邮件、来源可信度和提取置信度；
- 去重依据，以及适用时被其替代的旧事件版本；
- 敏感级别；
- 适用时的金额、币种和掩码后参考号。

缺少的信息必须保持未知，不得用常识、邮箱接收时间或 Agent 猜测补齐。

事件事实之外，系统可以生成“紧急程度、潜在后果、建议动作和建议最晚安全时间”等评估信息，但必须逐项标记为规则判断、插件推断、Agent 建议或用户确认。建议最晚安全时间无法可靠计算时必须保持未知，不得伪装成邮件原始期限。

### 8.3 事件类型

插件至少必须区分以下事件类型：

- 预订创建、确认、出票、值机开放；
- 时间变化、地点变化、参与安排变化；
- 延误、取消、失败、服务中断；
- 截止日期建立、提前、延后或失效；
- 预约创建、确认、改期或取消；
- 账单出具、付款到期、自动付款已安排；
- 付款失败、支付成功、款项入账、明确逾期；
- 退款申请、退款处理中、退款完成；
- 续费将发生、价格变化、取消窗口将关闭；
- 需要回复、联系、感谢、祝贺、安慰、修复、确认、签署、补件、准备或到场；
- 证件或资格即将到期；
- 重要配送或上门服务时间窗口。

## 9. 状态与闭环语义

### 9.1 生命周期状态

| 状态 | 含义 |
| --- | --- |
| `tentative` | 只是申请、候补、意向或预订处理中，尚未确认 |
| `confirmed` | 官方已经确认、出票或接受 |
| `scheduled` | 动作已经安排，但尚未证明完成 |
| `completed` | 非资金动作已有可靠完成证据 |
| `paid` | 付款机构已确认支付成功，但尚未证明款项完成入账 |
| `posted` | 资金已经被相关机构确认入账 |
| `cancelled` | 事项已经取消，不应继续按原计划提醒 |
| `failed` | 付款、出票、预约或其他动作明确失败 |
| `refunding` | 退款已经发起但尚未完成 |
| `refunded` | 退款已经完成 |

一个事件在当前时点只能有一个生命周期状态。取消与退款必须表示为相互关联但不同的事件或状态对象，使“原行程已取消、退款仍在处理中”能够同时成立。

### 9.2 变化与证据状态

生命周期状态之外，每个事件必须分别表达：

- **变化标记**：时间、地点、金额、对象、责任人、状态或期限是否发生关键变化，以及变化发生时间；
- **证据状态**：`sufficient`（证据足够）、`incomplete`（证据不完整）、`conflicted`（来源冲突）或 `unverified_source`（来源无法核验）。
- **期限状态**：`not_due`（尚未到期）、`due_today`（今天到期）、`overdue`（权威来源或确定期限表明已逾期）、`no_deadline`（没有期限）或 `unknown`（期限不足以判断）。

生命周期、变化、证据和期限状态可以同时存在。例如“账单付款仍为 `scheduled`，但已经 `overdue`”；或者“行程仍为 `confirmed`，但出发时间刚刚变化，且新时间与另一来源冲突”。`changed`、`needs_verification` 和 `overdue` 不得作为生命周期状态覆盖当前真实业务状态。

### 9.3 闭环规则

- “已安排”不得自动等同于“已完成”。
- 信用卡自动还款已设置或转账已预约，只能标记为 `scheduled`。
- 只有发卡行或付款机构确认支付成功，才可标记为 `paid`；确认入账后才可标记为 `posted`。
- 预订申请不能等同于出票或正式确认。
- 退款处理中不能关闭退款提醒；只有明确退款完成才闭环。
- 用户的明确完成确认可以作为闭环依据，但必须与邮件来源事实区分。
- 仅仅没有发现后续邮件，不能推导为失败、逾期或未完成。

## 10. 去重、变更与冲突

### R4 邮件去重

同一邮件被重复转发、重复投递或多次处理时，用户可见的逻辑来源和事件不得重复。系统仍须保留每次投递与处理尝试的审计事实。去重不能仅依赖主题、转发时间或正文相似度。

### R5 事件去重

同一真实订单、行程、账单、预约或活动在多封邮件中出现时，应关联到同一事件链，不得把一次变更显示成两个并行有效的安排。

### R6 最新状态覆盖当前视图但不删除历史

新通知确认改变旧安排时，当前视图必须采用最新且更权威的信息；旧邮件和旧状态仍须保留为可回源历史。只有来源身份和业务版本都具有可比性时，才可判断“更新且更权威”；否则必须按冲突处理。

### R7 冲突不得静默选择

如果两个来源对时间、地点、金额或状态给出互不兼容的信息，且无法确定谁更新或谁更权威，事件的证据状态必须为 `conflicted`，并向 Agent 明确暴露冲突点。

### R8 领域去重要求

- 交通事件优先按承运方、日期、班次及掩码订单参考号关联；
- 住宿事件优先按住宿方、城市和入住日期关联；
- 账单事件优先按机构、账期、币种和掩码账户参考号关联；
- 日程事件优先按组织方、时间、地点和参与对象关联。

这些关联条件用于表达业务要求，不限定未来采用的具体算法。

## 11. 时间、地点与实时性

- 时间必须区分精确时刻、当地日期、时间窗口和仅保留原文的模糊表达。
- 精确时刻必须保留明确时区；邮件没有给出时区时，必须标记待核对，不得仅按服务器时区解释。
- 只有日期、没有时刻的期限不得为满足格式要求而虚构时间或时区。
- 跨时区行程必须分别保留出发地与到达地当地时间。
- “在某日之前”“当天”“工作日”等模糊表达必须保留原文语义，并标记解释的不确定性。
- 订单邮件只能证明预订或通知状态，不能证明航班、列车、天气或交通在查询时刻的当前运行状态。
- Agent 在临近出发时必须能够区分“邮件已确认”和“实时状态尚未核验”。
- 地点改变、车站或机场改变、航站楼改变必须作为关键变化，而不能只更新一段说明文字。

## 12. 金融提醒要求

插件只管理付款期限和闭环状态，不管理资金账户本身。

必须提取：

- 机构名称；
- 卡片或账户末四位；
- 账单金额、最低还款额和币种；
- 明确还款日；
- 自动扣款已安排、失败、支付、入账或逾期状态；
- 来源邮件日期和来源可信度。

不得向 Agent 输出：

- 完整卡号或账号；
- CVV、PIN、验证码和登录信息；
- 与提醒无关的逐笔交易明细；
- 邮件中的付款链接、二维码或未经核实的联系电话。

金额、机构或来源存在疑问时，提醒必须要求用户在官方 App 或官方渠道核对。

“金额异常”只有在以下至少一项成立时才可使用：权威来源明确标记异常、存在可证实的重复扣款、违反用户明确设置的阈值，或显著偏离具有足够数据支持的历史基线。模型不得仅凭主观感觉把金额标记为异常。

### 12.1 语言与地区格式

- 首版必须正确处理英文、简体中文、繁体中文及三者混合的主题、正文和附件文字。
- 人名、机构名、地点名、班次、货币和订单参考信息必须保留原文，不能因翻译改变实体身份。
- 日期、月份、星期、十二小时制、二十四小时制、小数点、千位分隔符和币种符号必须结合邮件语言与地区解释。
- 原文存在多种可能解释时必须标记待核对，不能依赖系统地区设置静默选择。
- 不支持的语言或无法可靠识别的地区格式必须进入部分解析或待人工复核，并明确未覆盖内容。

## 13. 责任人与本人判断

- 只有邮件明确表明用户本人负责、必须由本人决定，或需要本人亲自维护关系时，才能标记 `requires_principal`。
- “团队需要完成”“公司需要回复”或抄送用户，不足以证明用户本人负责。
- 他人的义务必须保留真实责任人；不能为了方便提醒而转嫁给用户。
- 邀请、纪念日或关系事项只有在对象、时间和期望动作足够明确时，才能生成关系事件。
- 对感谢、祝贺、安慰、修复或道歉的建议必须与邮件明确事实分开标注，不能冒充对方要求。

## 14. Agent 读取能力

获授权 Agent 至少必须能够：

1. 获取指定日期和时区下的简报候选；
2. 查询指定时间范围和分类的有效事件；
3. 查询最近发生的关键变化；
4. 查询尚未闭环的义务和期限；
5. 查看单个事件的当前状态、历史和来源；
6. 按发件方、主题、日期和关键词查找来源邮件；
7. 获取与某项判断直接相关的脱敏原文片段；
8. 获取邮箱数据覆盖截止时间、失败数量和未解析数量；
9. 区分邮件事实、插件推断、Agent 建议和用户确认；
10. 在来源不足或冲突时得到明确的“需要核对”，而不是伪造确定答案。

Agent 默认不得获得以下能力：

- 发送、回复、转发或移动邮件；
- 未经用户或邮箱管理员对精确删除计划显式授权，直接删除、批量清理或永久擦除邮件及其派生数据；
- 打开或执行邮件中的链接、二维码和附件脚本；
- 修改事件来源、伪造闭环或覆盖历史；
- 发起付款、改签、取消、签署、登录或身份验证；
- 扩大到私人或工作主邮箱进行搜索。

## 15. 每日简报候选规则

### 15.1 “今天必须决定”的准入门槛

事件只有满足以下至少一项，才可成为“今天必须决定”的候选：

- 今天到期，或今天不行动就会失去合理处理窗口；
- 未来 24 小时内出发、值机、到场或交付，且存在未确认或衔接风险；
- 航班、车次、酒店、地点、时间或预约发生关键变化；
- 自动扣款失败、官方明确逾期或金额异常；
- 取消、退款、签证、补件或续费窗口将在 72 小时内关闭；
- 与已经确认的会议、家庭承诺、行程或必要恢复时间发生冲突；
- 必须由用户本人回复、签署、确认、拒绝或处理关系；
- 不处理可能造成明显失信、财务损失、信用影响或人身安全风险。

最终输出必须是 0–3 项，宁缺毋滥，不得为了版式凑满。超过 3 项达到门槛时，按以下需求级原则综合排序：

1. 人身安全或不可逆损失；
2. 最晚安全行动时间更近；
3. 明确必须用户本人处理；
4. 失信、关系、财务或信用后果更严重；
5. 证据更充分，或虽然证据不足但核验本身已经紧迫。

达到门槛但未进入前三项的候选仍必须可查询，不能因版面限制而消失。

### 15.2 不进入前三项

- 普通预订确认；
- 远期且无冲突的行程；
- 已有可靠闭环证据的事项；
- 只提供资讯、营销或推荐的邮件；
- 可以无损延后、委派或忽略的事项；
- 责任人不是用户本人且不需要本人决定的事项。

### 15.3 候选表达

每项候选必须能够回答：

- 决定或确认什么；
- 最后期限是什么；
- 为什么必须今天处理；
- 建议采取什么最小动作；
- 是否必须本人处理，还是可以委派；
- 依据哪封邮件，是否还需到官方渠道核验。

## 16. 安全与隐私要求

### R9 最小披露

Agent 默认只能看到完成当前判断所需的最少字段和脱敏片段。完整原文和附件不能因为“读取方便”而默认提供。

### R10 敏感信息掩码

银行卡号、银行账号、证件号、会员号、票号和订单号在提供给 Agent 或进入简报时最多显示末四位；验证码和凭证不得显示任何有效内容。

### R11 提示词注入隔离

邮件中出现的“忽略之前规则”“调用某工具”“发送资料”“点击链接”等文字只能作为邮件内容，不得改变 Agent 的角色、权限、任务、工具选择或数据访问范围。

### R12 外部行动隔离

即使邮件内容看起来紧急或由可信机构发送，插件和 Agent 也不得据此直接执行付款、登录、改签、签署或对外通信。需要行动时，只能提出建议并引导用户回到官方渠道。

### R13 授权可撤销

用户本人或邮箱管理员必须能够撤销 Agent 读取权限；撤销后，既有会话、派生结果和任何其他副本都不得继续取得被撤销范围的数据。

### R14 可审计

系统必须能回答哪个 Agent 在什么时间读取了哪些事件或来源范围。审计信息不得反过来泄露完整邮件秘密。

### R15 数据保留与删除

用户必须能够分别控制原始邮件、附件、结构化事件和审计记录的保留期限，并能够请求删除。删除前必须能说明将影响哪些原件、派生事件、搜索片段和审计信息；若某类审计因明确义务不能同步删除，必须提前说明范围和期限。具体默认期限和删除实现留待技术设计，但不得无限期保留而不给用户选择。

Agent 可以生成清理或删除计划；只有用户或邮箱管理员通过可信界面对计划所列精确对象、影响范围、恢复期限和计划哈希显式授权后，Agent 才可触发对应的一次性执行。Agent 不得自行扩大计划、缩短恢复期限、删除审计记录或绕过永久擦除的额外确认。

## 17. 人工治理要求

邮箱管理员必须能够：

- 查看已接收、已拒绝、未解析和存在冲突的邮件；
- 配置允许的发送方、来源域名、主题条件和排除条件；
- 将误分类邮件改为正确分类；
- 合并重复事件或拆分被错误合并的事件；
- 修正时间、时区、地点、责任人和状态；
- 标记某项已经由用户在其他渠道完成；
- 持续排除某个发送方或邮件，直至管理员撤销该规则；
- 查看修正前后差异和修正人；
- 重新处理失败邮件而不重复生成事件；
- 查看最新成功接收时间和数据覆盖缺口。

人工修正必须与原始邮件事实并存，不能改写或删除原始来源。后续自动处理不得静默覆盖人工确认的字段。

## 18. 异常与失败行为

- 无法解析邮件时必须保留失败状态和原因，不能当作“无事项”。
- 附件损坏、加密或格式不支持时，必须说明哪些信息未被读取。
- 来源身份异常、邮件认证失败或疑似钓鱼时，必须降低可信度并禁止暴露可执行链接。
- 同一事件出现相互冲突的有效通知时，必须提示核对，不能按接收顺序武断覆盖。
- 时区、金额、币种、责任人或期限不明确时，必须保留未知状态。
- 接收或处理发生中断时，Agent 必须能看到覆盖截止时间，不能把旧数据描述成最新状态。
- 已取消的事件不得继续按原时间提醒；取消后的退款尚未完成时，退款事件仍须保留。
- 用户确认完成但随后收到官方失败通知时，必须重新打开风险并显示冲突来源。

## 19. 验收标准

首版只有同时满足以下条件，才可视为达到需求：

1. 只配置一个专用邮箱，即可完成从投递、准入或隔离、解析、生成或不生成事件，到 Agent 查询和撤销授权的端到端流程。
2. 专用 envelope recipient 始终精确校验且不可关闭；用户可在最长一小时的转发验证期关闭 sender filter 并看到明确风险提示，超时自动恢复严格过滤；确认后可保存唯一 Gmail 地址并启用严格过滤，使其他 envelope sender 在任何正文或附件持久化之前被拒绝且不进入本地同步流。
3. 已批准的代表性测试集覆盖全部 14 类业务邮件，每类至少有一个有效样本；整套样本同时覆盖确认、变更、取消、失败和闭环通知及其关键字段。不支持或不确定的样本进入待人工复核，而不是误判为无事项。
4. 投递处理结果能明确区分待处理、已生成事件、已解析无事件、部分解析、待复核、隔离、拒绝和处理失败。
5. 以凭证、验证码、身份恢复或其他禁止内容为主体的邮件不会生成正常事件，也不会进入 Agent 可搜索的正文或片段。
6. 合法通知夹带敏感内容时，Agent 只能取得准入范围内的必要安全字段。
7. 收件、预览、解析和查询不会自动加载邮件远程资源或执行附件主动内容。
8. 同一邮件重复投递不会重复生成用户可见来源或事件，同时仍能审计每次投递和处理尝试。
9. 直接来源、可信转发、内层声称来源和不可核验来源能被区分；转发层认证不会被错误继承给原始发送方。
10. 每个事件只有一个主要分类；一封跨领域邮件可以生成多个不同分类的事件。
11. 无法可靠分类但可能有行动价值的邮件进入待人工复核，不会静默丢弃。
12. 生命周期状态、关键变化、证据状态和期限状态能够同时表达，不会互相覆盖。
13. 同一真实事件的确认、变更、取消和退款能形成连续状态历史。
14. 一封包含多个时间节点的邮件能生成多个相关事件。
15. 新状态可以更新当前视图，但不会抹去旧邮件和旧状态。
16. 无法判断的新旧冲突会显示冲突字段、相关来源和“需要核对”。
17. 精确时刻保留明确时区或标记时区未知；日期型期限不会被虚构为某个时刻。
18. 跨时区行程能正确区分出发地和到达地当地时间。
19. 预订申请不会被误判为出票或正式确认。
20. 自动付款已安排、支付成功和款项入账能被分别表达。
21. 退款处理中不会被误判为退款完成。
22. 已取消事件不会继续作为原计划提醒，但关联的未完成退款仍可提醒。
23. 金额异常只依据权威标记、可证实重复、用户阈值或充分历史基线，不由模型凭感觉判断。
24. Agent 能查询当天候选、近期事件、最新变化、未闭环事项和来源依据。
25. Agent 能看到邮箱覆盖截止时间、待复核数量、部分解析范围和处理失败情况。
26. “今天必须决定”输出为 0–3 项；超过 3 个合格候选时按本规格排序，其他高风险候选仍可查询。
27. 简报候选明确区分来源事实、系统评估、Agent 建议和用户确认，并包含决定、期限、今天处理的理由、建议和来源状态。
28. 已完成、低价值、纯营销和非用户本人责任事项不会挤占当天前三项。
29. 完整账号、卡号、证件号、票号和订单号不会出现在 Agent 输出中。
30. 验证码、密码重置和其他凭证内容不会出现在事件、搜索结果、摘要、日志或审计详情中。
31. 邮件中的指令无法改变 Agent 权限或触发外部动作。
32. Agent 无法通过插件发信、付款、登录、签署、改签或取消。
33. 系统能审计哪个 Agent 在什么时间读取了哪些事件或来源范围，同时不泄露完整秘密。
34. 人工修正有记录，且不会被后续自动处理静默覆盖。
35. 用户可以分别管理原始邮件、附件、派生事件和审计的保留与删除范围，并在删除前看到影响说明。
36. 权限撤销后，任何既有会话、副本或派生结果均无法继续取得被撤销范围的数据。
37. 当邮箱数据缺失、过期或处理异常时，系统明确降级，不声称信息完整。
38. 用户手动转发会标记相关性，但不会被当作真实性确认、责任确认或外部行动授权。
39. 英文、简体中文、繁体中文及混合语言的代表性样本能正确保留实体和解释地区格式；不确定或不支持内容会降级而不是猜测。
40. Agent 默认不能删除；Agent 生成的删除计划只有在可信插件界面对精确对象、影响范围和计划哈希确认后才能执行，重复、过期、被撤销或目标已变化的计划不会造成额外删除。

## 20. 留待后续技术设计决定

以下问题不在本文裁决，后续技术设计必须逐项给出方案并证明满足上述需求：

- 邮件如何接收、验证、持久化和恢复；
- 原始邮件、附件、事件与审计分别使用什么数据载体；
- Agent 通过什么协议和身份体系访问；
- 如何实现来源认证、去重、版本关系和人工修正保护；
- 如何解析 HTML、日历邀请、PDF、图片和加密附件；
- 各类数据的默认保留期限、删除语义和备份恢复；
- 如何隔离租户、设备、测试环境和生产环境；
- 如何监控投递失败、解析积压、数据延迟和服务可用性；
- 是否需要用户界面，以及首版人工治理功能以何种形态提供；
- 如何验证模型抽取质量、事件合并质量和提示词注入防护。

无论采用何种实现，后续设计不得弱化本文的单邮箱范围、只读 Agent、最小披露、来源可追溯、状态不混淆和外部行动隔离要求。
