# 产品原则:让 agent 干活的规程,也是你的资产——它归 vault,不归 harness

> 状态:产品原则 / 外宣素材(2026-10-23 提出,作为第六条信念)
> 适用:vault 内一切「让 agent 做事的规则与描述」——`AGENTS.md`、`SOUL.md`、skills、定时任务(cron)、MCP 连接、Memory(`USER.md` / `MEMORY.md`)及同类文件

## 一句话

> 一个与 agent 共用的个人 vault,保管着两类数据:一类是**内容**——agent 写的文档、你留下的判断;另一类是**规程(Playbook)**——告诉每个 agent 该守什么规矩、会什么本事、什么时候干活、能碰什么工具、该记住你什么。内容是 agent 干出来的活,规程是让 agent 干得好的那套"怎么干"。**规程同样是只有你才写得出的字,它必须住在 vault 里,而不是散落在各家 harness 的私有目录中。**

---

## 现象:规程是长期使用后才浮现的资产

用一段时间多 agent 协作之后,会发现真正在复利的不只是笔记,而是这些东西:

| 层 | 典型载体 | 回答的问题 |
| --- | --- | --- |
| 规矩 | `AGENTS.md` / `CLAUDE.md` | 在这里干活要守什么约定、什么不能碰 |
| 身份 | `SOUL.md` 等人格文件 | 这个 agent 是谁、替谁做事、口吻与底线 |
| 技能 | `SKILL.md`(skills) | 某一类活具体怎么做才算做对 |
| 排程 | cron / 定时任务 | 什么时候、无人值守地做什么 |
| 连接 | MCP 配置 | agent 能触达哪些工具和数据 |
| 记忆 | `USER.md` / `MEMORY.md` | agent 该知道你的哪些事实与偏好 |

(子 agent 定义、hooks、提示词模板属于同一类,按同一原则处理。)

它们有四个共同点:

1. **杠杆极高。** 一篇文档只影响它自己;`AGENTS.md` 里一行字影响此后每一次运行,一条 cron 每晚替你开工。
2. **是判断的结晶。** 每条规矩背后往往是一次被纠正、一次踩坑、一次"以后别这样"。它是信念 1 所说的"残余"中最可复用的那部分——不是对一篇文档的判断,而是对**工作方式**的判断。
3. **今天天然是碎片化的。** Claude Code 读 `.claude/`,Codex 读 `~/.codex/`,OpenClaw 有自己的定时任务表,每个 MCP 客户端一份配置。换一家 harness,"怎么干"就得重写一遍——这正是信念 5 想消灭的那种锁定,只是藏得更深。
4. **错了的代价是被反复执行。** 内容出错,最坏是被检索出来、被读错;规程出错,会在此后每一次运行里被**执行**。坏的技能文件会把坏流程永远固定下来。内容要值得被检索,规程要值得被执行。

## 核心主张

**把规程当作 vault 的一等数据集,与内容并列管理:vault 里的那份是唯一事实源,各家 harness 读到的是它的投影。**

- **单一事实源在 vault。** 规程以纯文本住在 vault(git 版本化、可 diff、可 grep、可 `git revert`)。`~/.claude/skills`、`~/.codex/AGENTS.md`、某个 harness 的 cron 表,都是从 vault 派生出的投影——就像信念 2 里"索引是派生数据,文件是唯一事实源"。
- **`AGENTS.md` 是规程的入口。** vault 根的 `AGENTS.md` 不只讲规矩,也是规程的目录:声明这个 vault 的 skills、排程、连接、记忆分别在哪里。任何 agent 进门先读它,就能找到全部"怎么干"。
- **改规程等于授权行为,只能由人确认。** agent 可以*提议*新增或修改一条规矩、一个 skill、一个排程(例如被纠正后写下的经验教训),但提议不等于生效。这与 Memory 中"行为授权"一义同源:规程的变更直接改变 agent 将来会做什么,因此**比改一篇普通文档的门槛更高**,而不是更低。
- **agent 不得给自己扩权。** 新增 MCP 连接、放宽可调用的工具、加一条无人值守的定时任务、改动谁能读哪段记忆——这些都必须由人确认。agent 写下的规程永远不得签 `human:`。
- **规程里只放引用,不放秘密。** MCP 配置、cron 任务常常牵涉令牌与凭据。进 vault、进 git 的是"连哪里、用什么名字引用凭据",凭据本身留在系统钥匙串或环境变量里。规程要能安全地推到 GitHub。
- **署名可读。** 每条规程都应看得出是谁写的、谁确认的(OKF 的 `generated` / `verified` 与 actor 格式)。看到一条规矩时,你应当能分辨"这是我定的"还是"这是某个 agent 提议、我点过头的"。

### 规程的生长:做过两次的事,提议成规程

规程不靠一次性设计出来,而是从干活中长出来:同一件事第二次被要求、同一个错第二次被纠正,就该沉淀成一条规矩或一个 skill。agent 可以主动做这件事——事后回看对话、夜间复盘,找出值得固化的流程和缺失的上下文——但产出只能是**待确认的提议**,附上它从哪次工作、哪次纠正而来。自动生长、人工准入:这是 note.md 与"agent 每晚自己改写自己的技能"的分界线。

### 规程的卫生规则

规程越多,越需要像管理内容一样管理它,而且标准更严:

- **每条都有来由。** 一条规矩应能追溯到它为什么存在:哪次纠正、哪个事故、哪份文档。没有来由的规矩,日后没人敢删,也没人敢改。
- **冲突只标记,不覆盖。** 新提议与已有规矩矛盾时(两个 skill 对同一件事给出相反做法、`AGENTS.md` 与某个 skill 打架),agent 标出冲突交给人裁决,而不是用新的悄悄盖掉旧的。
- **定期修剪。** 规程会过时:换了工具、换了流程、换了人。规程可以带 `stale_after`,到期后提示复核;长期未被调用的 skill、已失效的排程应被提出来供人决定保留还是归档。
- **热与冷分层。** 每次运行都要加载的规矩要短而硬;只在特定活儿里用的 skill 按需加载。别让 `AGENTS.md` 长成谁都读不完的百科。

### 两类计算各归其位

规程里有两种东西,放错位置本身就是缺陷:

- **判断与品味**——什么算好、何时该停、对谁用什么口吻——写成 Markdown 的规矩与 skill,交给模型。
- **确定性的步骤**——算数、查询、格式转换、按时触发——写成脚本与排程,交给代码。

把该写成代码的事塞进 Markdown,agent 会每次"重新理解"一遍并且偶尔理解错;把该交给判断的事写死在代码里,规程就失去了弹性。对确定性部分,agent 可以提议参数,但改动计算本身须人确认——与 OKF 的 Attested Computation 红线同一精神。

## 为什么这样更好

1. **反锁定推进到"怎么干"这一层。** 信念 2 让知识不被应用锁住,信念 5 让工作不被 agent/模型锁住;但如果规程散在各家目录里,换 harness 时丢掉的恰恰是最贵的那部分。规程归 vault,新来的 agent 第一天就按你的方式干活。
2. **复利。** 每一次纠正都沉淀成一条可被所有 agent 复用的规矩,而不是只教会了当时那一个会话。vault 用得越久,所有 agent 一起变好。
3. **带得走。** 规程是你工作方式的可执行形态。它在你的 vault 里,换工具、换团队、换工作时跟你走;它在别人的系统里,你的判断就留在了那里,替别人继续运行。
4. **可审计。** 规程在 git 里,"上周起 agent 为什么开始这样做"有答案:看那次提交、看谁提议、谁确认。
5. **安全边界清楚。** 规程决定 agent 能做什么。把它放在人看得见、改得了、回得退的地方,并要求扩权必须人确认,是"人在环内"在权限层面的落实。

## 可外宣的凝练版

> **让 agent 干活的规程,也是你的资产。**
> 你的 vault 不只存 agent 写下的东西,也存它们该怎么干活:`AGENTS.md`、skills、定时任务、MCP 连接、记忆。这些规矩是你一次次纠正、踩坑后留下的判断,每一行都会在此后每一次运行里被执行。所以它们住在 vault 里、由 git 记录、标明来由、经你确认才生效——agent 可以提议,你来准入;换哪家 agent,都按你的方式干活。

> **The playbook that runs your agents is yours, too.**
> Your vault holds more than what agents write. It holds how they should work: `AGENTS.md`, skills, schedules, MCP connections, memory. Every rule in it is a judgment you made after a correction or a mistake, and each line is executed in every run that follows. So it lives in the vault, is tracked by git, records why each rule exists, and takes effect only when you confirm it. Agents propose; you admit. Whichever agent you hire, it works your way.

## 与既有原则的关系

这一条把前五条信念从"内容"延伸到"规程":

- **信念 1(判断是残余)**——规程是对工作方式的判断,是最可复用的残余。
- **信念 2(文件高于应用)**——规程是纯文件;harness 私有目录里的副本是派生投影。
- **信念 3(它建议,你确认)**——agent 可以提议规程变更,生效只在你确认处;扩权的门槛最高。
- **信念 4(批注属于 vault,不属于路径)**——同构:散落在各 harness 路径下的规程,也应在 vault 里获得稳定的、git 版本化的宿主。
- **信念 5(一个 vault,多个 agent)**——规程是多 agent 编排得以跨 harness 移植的那份"公共工单";没有它,"你是编排者"只能每次口头重讲一遍。

合起来:**知识归你,判断归你,让 agent 干活的规矩也归你。**

## 外部参照:GBrain 的半年演进

Garry Tan 的开源记忆层 GBrain 在 2026 年 4–10 月的演进,从外部印证了这条原则,也标出了我们的分界(依据其 10 个公开视频字幕整理的阅读笔记,数字均为本人自述):

- **技能的归属是所有权问题。** 他在 YC Startup School([Own Your Intelligence](https://www.youtube.com/watch?v=eRrc1pUY5oU),2026-08)用一位工程师的 40 个技能举例:技能在她自己的仓库里,换工作时能带走;在公司仓库里,公司离开她也能继续运行她的判断——"拥有你的技能,否则你的工作会变成一个技能文件"。对应上文"带得走"。
- **harness 变得无所谓,库才是资产。** GBrain 从"给我的 OpenClaw 用的 RAG"变成适配任何 harness 的记忆层([Supabase · Tiny Teams](https://www.youtube.com/watch?v=SSfig1Z0E3c),2026-10)。对应"vault 为源,harness 为投影"。
- **库越大,卫生越重要。** 他的重心从"检索做得好"移到"值得被检索",并点名故障:没人策展的库变成"搜索很好用的垃圾场",坏的技能文件把坏流程永远固定([AI Engineer · Every company should have a Brain](https://www.youtube.com/watch?v=eBUyTS7SzV4),2026-07)。对应"规程的卫生规则",我们把它从内容推到规程上。
- **两类计算。** 判断交给模型,算术与查询交给代码;agent 系统出错多半是放错了层([Stanford CS153](https://www.youtube.com/watch?v=Lri2LNYtERM),2026-05)。对应"两类计算各归其位"。
- **托管权就是安全模型。** 库跑在自己的设施、仓库和密钥下。对应"规程只放引用,不放秘密"。

**分界在准入。** GBrain 的库"大部分由 agent 写成",梦境循环每晚回看对话、改进技能,skillify 把做过的事直接变成技能,人主要在事后修剪。note.md 保留同样的生长机制,但把它们的产出定为提议:规程只在你确认处生效。理由是信念 3,也是上文第 4 个共同点——规程错了会被反复执行,准入必须在生效之前,而不是在出事之后。

## 工程落点(实现锚点)

已有:

- vault 根 `AGENTS.md`,OKF `type: Vault Conventions`(见 `src/lib/okf/concept.ts`)。
- Memory 的权威修订在 `.notemd/memory/`,`USER.md` / `MEMORY.md` 是可重建的投影;候选记忆经人逐条确认(见 llms-full.txt「Controlled personal Memory」)。
- 公共约定通过 `website/public/llms.txt` / `llms-full.txt` 对所有 agent 公开。

待建 / 待定(开放问题,落地前需单独设计):

1. **目录布局。** skills、排程、连接在 vault 内的规范路径;是否兼容各 harness 已有约定,还是由 `AGENTS.md` 声明位置即可。
2. **投影方向与冲突。** vault → harness 的投影(同步、软链接或导出命令)如何实现;harness 侧被直接修改时,如何回流成"待确认的提议"而不是静默覆盖。
3. **OKF 一致性。** `SKILL.md` 等 harness 原生文件自带的 frontmatter 没有 `type`。note.md 写入时是否补 `type`(需在 `CONCEPT_TYPE` 登记新类型),还是把这些文件视为外来文件、一字不动。
4. **提议与确认的界面。** 规程变更的审阅是否复用 Memory 的确认流程(确认 / 否认 / 忽略),以及如何高亮扩权类变更。
5. **秘密检测。** 写入或提交规程前,对令牌、密钥做本地检查并拦截。
6. **来由与冲突的记法。** 每条规矩的来由记在哪里(frontmatter `sources`、行内脚注,还是 git 提交信息);冲突标记用什么格式,才能让任何 harness 都认得。
7. **复盘提议的入口。** 夜间复盘、skillify 这类机制产出的提议放在哪里、以什么形态等待确认;已忽略的提议如何去重,避免同一个建议每晚回来。
8. **修剪信号。** 用什么判断一个 skill "长期未被调用"——需要 harness 侧的调用记录,而这些记录本身不应成为新的私有状态。
